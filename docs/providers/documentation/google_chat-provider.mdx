## Connecting with the Provider

1. Open Google Chat
2. Open the space to which you want to add a webhook
3. Next to the space title, click the expand more arrow, and then click "Apps & Integrations"
4. Click "+ Add webhooks"
5. In the Name field, enter "Quickstart Webhook"
6. In the Avatar URL field, enter https://developers.google.com/chat/images/chat-product-icon.png
7. Click Save
8. To copy the webhook URL, click "More", and then click "Copy link".

## Delivery behavior

The provider sends text messages to the configured incoming webhook. It does not
currently create cards or message threads.

Requests use a 5 second connection timeout and a 15 second read timeout. The
provider makes at most three attempts for network failures, HTTP 408, HTTP 429,
and HTTP 5xx errors. Other non-success status codes fail without retrying.
Retries use exponential delays and honor a valid `Retry-After` header. If the
requested delay exceeds 60 seconds, delivery fails instead of retrying before
the server allows or keeping the worker in a longer server-directed sleep.

Google Chat applies quotas per space, shared by all incoming webhooks in that
space. These bounded retries are not a shared rate limiter or durable delivery
queue. A timeout after Google accepted a message can still lead to a duplicate
on retry. Workflow-level retries also multiply the provider's attempt count.

See [Google Chat webhook limitations](https://developers.google.com/workspace/chat/quickstart/webhooks#limitations_and_considerations).

## Optional shared-space pacing

Set `GOOGLE_CHAT_RATE_LIMIT_ENABLED=true` in every Keep process that runs
workflows, with Keep's existing `REDIS=true` configuration, to coordinate
notification attempts across provider aliases and workers. All processes must
use the same Redis database. No additional service or delivery queue is created.
The default is disabled for compatibility.

The limiter identifies the Google Chat Space from the webhook path, regardless
of webhook token, provider alias, workflow, tenant, or client. It stores only a
hash of the Space ID and an expiring permit. Each HTTP attempt must acquire a
permit, with at least 1.1 seconds between permits for a Space. Different Spaces
remain independent. This applies to retries as well as first attempts.

A busy Space waits for at most 60 seconds per attempt. Redis errors, missing
Redis configuration, invalid webhook paths, and exhausted waits fail the action
explicitly before its HTTP request; they do not silently skip a notification or
bypass rate limiting. A permit expires automatically if its worker stops. Direct
Redis settings are taken from Keep's existing Redis configuration, including
its TLS and authentication settings. Sentinel discovery reuses Keep's existing
configuration behavior; separately authenticated or TLS-protected Sentinel
endpoints are not supported by this change. It does not add new Sentinel
credentials or claim production Sentinel validation.

This is bounded pacing inside the existing workflow executor, not a durable
outbox. Waiting uses a workflow worker. Monitor workflow errors and backlog, keep
spare workers for independent audiences, and recover failed deliveries through
the workflow execution history. A process restart or a timeout after the remote
server accepted a message can still require assisted recovery or produce a
retry duplicate. Other applications using the same Space must also be included
in its capacity assessment. Redis must be shared, available and protected from
eviction for the limiter's keys; resetting it removes recent permits. The
1.1-second permit interval reduces quota collisions but HTTP scheduling pauses
and traffic outside Keep can still produce 429 responses, handled by the bounded
retry policy above.
