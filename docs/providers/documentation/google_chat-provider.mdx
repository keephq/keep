## Connecting with the Provider

1. Open Google Chat
2. Open the space to which you want to add a webhook
3. Next to the space title, click the expand more arrow, and then click "Apps & Integrations"
4. Click "+ Add webhooks"
5. In the Name field, enter "Quickstart Webhook"
6. In the Avatar URL field, enter https://developers.google.com/chat/images/chat-product-icon.png
7. Click Save
8. To copy the webhook URL, click "More", and then click "Copy link".


## Posting to more than one space

`webhook_url` in the provider configuration is the default target and is
optional. A single provider can serve every space instead of one provider per
space.

### Addressing a space by name

`webhook_urls` holds the webhooks, keyed by a name you choose:

```json
{
  "platform-alerts": "https://chat.googleapis.com/v1/spaces/AAAA.../messages?key=...&token=...",
  "network-alerts": "https://chat.googleapis.com/v1/spaces/BBBB.../messages?key=...&token=..."
}
```

A workflow then names the space it wants:

```yaml
actions:
  - name: post-to-chat
    provider:
      type: google_chat
      config: "{{ providers.google-chat }}"
      with:
        space: "{{ alert.chat_space }}"
        message: "{{ alert.name }}"
```

Combined with a [mapping rule](/overview/enrichment/mapping), the routing table
becomes data: the rule matches on alert fields and enriches the alert with the
name of the space that should receive it.

This is the preferred way to route between spaces. A webhook URL carries its
`key` and `token` in the query string, which makes it a credential, and a space
name is not one. Keeping the names in the mapping rule and the URLs in
`webhook_urls` means the credential stays in the secret manager, while what
travels through alert enrichment is only a name.

Every URL in `webhook_urls` is validated when the provider is configured, so a
malformed or non-Chat entry fails immediately rather than on the first alert.

### Passing a webhook URL directly

An action can also pass the URL itself, which overrides both `space` and the
configured default:

```yaml
      with:
        webhook_url: "{{ alert.chat_webhook }}"
        message: "{{ alert.name }}"
```

<Warning>Prefer `space` for anything driven by alert data. A `webhook_url` taken
from an enriched alert field means the credential is stored with the alert.</Warning>

Only `https://chat.googleapis.com` is accepted, whatever the source of the URL.

## Cards and threads

`cards_v2` sends a [cardsV2](https://developers.google.com/chat/api/guides/v1/messages/create#create)
payload, on its own or together with `message`:

```yaml
      with:
        message: "{{ alert.name }}"
        cards_v2:
          - cardId: "alert"
            card:
              header:
                title: "{{ alert.name }}"
                subtitle: "{{ alert.service }}"
```

`thread_key` groups messages into a thread. Messages sharing a key land in the
same thread, and an unknown key starts a new one, so keying on the alert
fingerprint keeps every update of an alert together:

```yaml
      with:
        message: "{{ alert.status }}"
        thread_key: "{{ alert.fingerprint }}"
```
