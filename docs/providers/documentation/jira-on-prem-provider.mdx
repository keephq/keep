## Auto-Transition Workflows

The on-prem provider moves a ticket between statuses with the same `transition_to` parameter as the
Jira Cloud provider, so a workflow written for one runs on the other by changing `type`.

Pass `transition_to` alongside `issue_id` to move an existing ticket, or alongside the fields of a
new ticket to create it and move it in one step. The name is matched against the transitions Jira
offers for that ticket, case-insensitively; an unknown name fails with the list of the ones that
exist:

```
Transition 'Invalid' not found. Available transitions: To Do, In Progress, Done, Closed
```

The personal access token needs the `TRANSITION_ISSUES` permission on the project.

```yaml
workflow:
  id: jira-on-prem-transition-on-resolved
  name: Transition Jira On-Prem Ticket to Done
  description: Close an on-premises Jira ticket when the alert behind it is resolved.
  disabled: false
  triggers:
    - type: alert
      cel: status == "resolved"
  actions:
    - name: jiraonprem-action
      provider:
        type: jiraonprem
        config: "{{ providers.JiraOnPrem }}"
        with:
          issue_id: "{{ alert.ticket_id }}"
          summary: "{{ alert.name }} - {{ alert.description }} (resolved)"
          description: "Alert has been resolved automatically by Keep."
          transition_to: Done  # Change to your workflow's status name
```

See the [Jira Cloud Provider](./jira-provider) page for the longer walkthrough, including how to find
the transition names your Jira workflow uses.
